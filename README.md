# rabotahrista

Установщик ноды Remnawave на чистый VPS: пользователь, харденинг SSH, фаервол,
fail2ban, тюнинг ядра, Docker, сама нода, сертификат Let's Encrypt и nginx,
плюс уведомления в Telegram.

## Установка на сервер

```bash
curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/setup.sh -o /tmp/setup.sh
sudo bash /tmp/setup.sh
```

Нужны права root. Обратите внимание: `sudo bash <(curl ...)` **не работает** —
sudo закрывает лишние файловые дескрипторы, а подстановка процесса это как раз
дескриптор. Поэтому сначала скачиваем в файл. Под самим root первая строка не
нужна, но скрипт отключает вход под root, так что после первой установки
заходить вы будете обычным пользователем. Скрипт задаёт вопросы,
показывает меню и в конце печатает отчёт с командой для входа и паролем.

Этого одного файла хватает на всё. Меню:

```
 1) Полная установка (чистый сервер)
 2) Доустановить/переустановить компонент
 3) Диагностика — что не так с этой нодой (ничего не меняет)
 4) Починка по итогам диагностики
 5) Диагностика + реальный тест продления сертификата
```

Обычный обход ноды — пункт 3, посмотреть, пункт 4, снова пункт 3.
То же самое без меню, если нод много:

```bash
sudo bash /tmp/setup.sh --check     # только посмотреть
sudo bash /tmp/setup.sh --repair    # починить и ничего не спрашивать
```

Неинтерактивная установка — с файлом ответов:

```bash
sudo bash /tmp/setup.sh /root/node.conf
```

За образец берите `config.example.conf`.

## Как устроен репозиторий

Главное, что нужно понять: **`setup.sh` в корне не редактируется руками.**
Это собранный файл — он существует потому, что на чистом сервере нет ни git,
ни репозитория, и туда должен приезжать один самодостаточный скрипт.
Исходники живут в `lib/`.

```
lib/00-header.sh      режимы оболочки, обработчик ошибок, все настройки
lib/10-helpers.sh     сводка шагов и печать итогового отчёта
lib/20-prompts.sh     все вопросы пользователю и проверка введённого
lib/30-state.sh       сохранение ответов между запусками, отправка в Telegram
lib/40-system.sh      swap, пакеты, sysctl, IPv6, ротация логов, автообновления
lib/50-security.sh    пользователь, харденинг SSH, UFW, fail2ban
lib/60-node.sh        Docker и контейнер remnanode
lib/70-web.sh         ACME-проверка, сертификат, Cloudflare DNS, nginx
lib/80-notify.sh      телеграм-уведомления и сервисы слежения
lib/82-panel.sh       сторож панели на дежурной ноде
lib/85-extras.sh      WARP, speedtest, диагностика
lib/90-install.sh     порядок шагов при полной установке
lib/92-repair.sh      починка уже настроенной ноды (пункт 4 и --repair)
lib/94-check.sh       диагностика (пункт 3, --check и весь check.sh)
lib/95-menu.sh        меню
lib/99-main.sh        точка входа (всегда последним)

build.py              собирает setup.sh и check.sh из lib/
.githooks/pre-commit  сборка и тесты перед каждым коммитом
check.sh              СОБРАННЫЙ файл: только диагностика, ничего не меняет
tests/                проверки, которые не требуют сервера
```

`check.sh` тоже не редактируется руками. Он собирается из `lib/94-check.sh`
плюс блок настроек из `00-header.sh` — то есть это ровно тот код, который
работает в пункте 3 меню. Тест сверяет обе копии побайтово: иначе «проверил
одним скриптом, починил другим» однажды перестало бы сходиться.

Файлы склеиваются по алфавиту имён — поэтому они пронумерованы.
`00-header.sh` обязан быть первым, `99-main.sh` — последним, это проверяется
при сборке.

## Рабочий цикл

Один раз на репозиторий включите хук — он собирает и проверяет за вас:

```powershell
git config core.hooksPath .githooks
```

Дальше цикл простой:

```powershell
# правите нужный модуль в lib/
git add -A
git commit -m "..."     # хук сам соберёт setup.sh и прогонит тесты
git push
```

Хук перед коммитом запускает `build.py`, добавляет пересобранный `setup.sh`
в тот же коммит и прогоняет все тесты. Если тесты красные — коммит не
состоится, и в репозиторий не попадёт заведомо сломанный установщик.
Обойти в крайнем случае: `git commit --no-verify`.

CI на GitHub делает то же самое ещё раз, но **ничего не коммитит**. Поэтому
`git pull` нужен только если вы правили что-то через веб-интерфейс GitHub.
Раньше бот пересобирал `setup.sh` сам и делал свой коммит — из-за этого
после каждого пуша требовался `pull`, а в сгенерированном файле возникали
конфликты.

Собрать и проверить вручную, без коммита:

```powershell
python build.py
bash tests/run-tests.sh
```

## Что проверяют тесты

Сервер для этого не нужен, всё гоняется локально за пару секунд:
`bash tests/run-tests.sh` — 19 групп, 53 проверки.

1. Синтаксис каждого модуля и собранного файла (`bash -n`).
2. Сборка: `setup.sh` совпадает с `lib/`, shebang на месте, переводы строк LF.
3. **Ни одна функция не заканчивается голым условием** — см. ниже.
4. Опросные функции возвращают 0, когда все ответы уже заполнены.
5. Мусор в `ADMIN_USER` / `SSH_PORT` откатывается на значения по умолчанию.
6. Порты ноды и WARP нигде не зашиты мимо переменных.
7. Повторная установка с настроенным Telegram доходит до конца.
8. Падение внутри функции печатает команду и имя функции, а не проходит молча.
9. Падение компонента не убивает меню.
10. Сохранённые ответы не выполняются как команды при следующем запуске.
11. Порт сверяется точно, а не по подстроке (22220 ≠ 2222).
12. Битый SSH-ключ отбраковывается до того, как отключат вход по паролю.
13. Диагностика в меню и в `check.sh` — байт в байт один код.
14. Диагностика не разоружает обработчик ошибок установщика.
15. Починка трогает SSH ровно тогда, когда харденинг слетел.
16. `shellcheck`, если установлен.

### Про пункты 3, 7, 8 — почему это отдельные тесты

Функция в bash возвращает код последней выполненной команды. Если последняя
строка — проверка вроде `[[ -z "$TG_TOPIC_ID" ]] && read ...`, то при
несовпадении условия функция вернёт 1. А вызов

```bash
[[ -n "$TG_BOT_TOKEN" ]] && ask_telegram
```

под `set -e` в этом случае завершает **весь скрипт**. Выглядело это так:
повторная установка на сервере, где Telegram уже настроен, обрывалась молча
сразу после строки `--- Telegram-уведомления ---`.

Молча — потому что ERR-трап без флага `set -E` не наследуется функциями.
Отсюда `set -eE` в `00-header.sh`: теперь любая авария печатает команду,
функцию, строку и код возврата.

Обратная сторона: ERR-трап срабатывает **даже при `set +e`**. Поэтому меню
запускает компоненты через `menu_step`, то есть внутри `if` — только там
подавлены и `set -e`, и трап. Пункт 9 следит, чтобы это не отменили.

## Диагностика живой ноды

Пункт 3 меню, либо `sudo bash /tmp/setup.sh --check`. Отдельный `check.sh`
остался для тех, кому нужен заведомо ничего не меняющий файл:

```bash
curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/check.sh -o /tmp/check.sh
sudo bash /tmp/check.sh           # быстрая проверка
sudo bash /tmp/check.sh --deep    # + реальный тест продления сертификата
```

Диагностика только читает — это проверяется тестом, а не обещанием. Запускать
на живой ноде безопасно в любой момент. Полную установку поверх работающей
ноды гонять НЕ нужно: она сбрасывает правила ufw, пересоздаёт контейнер и
уходит в перезагрузку. Чините точечно: пункт 4 или меню компонентов.

## Починка уже работающей ноды

Пункт 4 меню, либо один проход без вопросов, когда нод много:

```bash
curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/setup.sh -o /tmp/setup.sh
sudo bash /tmp/setup.sh --repair
```

Режим сам вычитывает настройки с ноды (домен из сертификата, IP панели из
правила ufw, секрет из compose, Telegram из notify.env) и исправляет права на
файлы с секретами, конфиг nginx и служебные скрипты уведомлений. Фаервол,
контейнер и пакеты не трогает, сервер не перезагружает.

### Отдельно про SSH

Хостеры после ремонта сервера оставляют в `/etc/ssh/sshd_config.d/` свои
дроп-ины. Имена вида `00-*.conf` читаются раньше нашего `01-hardening.conf`,
а sshd берёт **первое встреченное** значение директивы — и вход под root с
паролями снова открыт, хотя файл харденинга на месте и порт правильный.
Диагностика такие файлы называет по именам, починка их комментирует
(с бэкапом рядом) и перезапускает sshd.

Починка при этом:

* не накатывает харденинг на ноду, где его никогда не было — это отключает
  вход по паролю и требует проверенный ключ, такое делается только руками
  через пункт 2 → 8;
* не дёргает sshd, если `sshd -T` показывает, что всё и так закрыто;
* берёт порт из нашего файла харденинга, а не из `sshd -T`, иначе закрепила
  бы чужой порт из перебившего дроп-ина;
* при неудаче откатывает харденинг, пока текущая сессия жива.

## Мониторинг панели

Связь односторонняя: панель сама подключается к ноде и держит постоянные
TCP-соединения. Нода к панели не ходит, поэтому о падении панели она узнаёт
по исчезновению этих соединений — плюс сама стучится в порт панели, чтобы
поймать жёсткое падение, при котором сокеты зависают в ESTABLISHED.

Включается на **одной** дежурной ноде (пункт 21 меню), иначе при падении
панели напишут все ноды разом. Тревога — после трёх провалов подряд, то есть
примерно через 6 минут: перезапуск панели это переживает, настоящее падение —
нет.

## Если что-то пошло не так

Скрипт печатает подробность аварии: строку, саму команду, код возврата и
функцию. Каждый шаг установки при этом изолирован — падение одного не роняет
остальные, а помечается как `[СБОЙ]` в итоговой сводке.

Харденинг SSH защищён отдельно: если после перезапуска sshd не начинает слушать
новый порт, скрипт различает две ситуации — «конфиг принят, применится после
перезагрузки» (ничего не трогаем, UFW держит открытым и старый порт) и «конфиг
вообще не читается» (откатываемся, пока текущая сессия жива).
