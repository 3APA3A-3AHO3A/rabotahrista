# rabotahrista

Установщик ноды Remnawave на VPS: учётная запись и харденинг SSH, фаервол,
fail2ban, тюнинг ядра, Docker, контейнер ноды, сертификат Let's Encrypt,
конфиг nginx и уведомления в Telegram.

Один скачанный файл закрывает весь жизненный цикл ноды: установка, диагностика,
точечная починка, смена домена.

## Установка

```bash
sudo curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/setup.sh -o /tmp/setup.sh
sudo bash /tmp/setup.sh
```

Нужны права root. Две частые ловушки:

* `sudo bash <(curl ...)` **не работает**: sudo закрывает лишние файловые
  дескрипторы, а подстановка процесса — это как раз дескриптор;
* `curl` без `sudo` упадёт с `Failure writing output to destination`, если
  `/tmp/setup.sh` остался от запуска под root. Каталог `/tmp` — sticky, чужой
  файл перезаписать нельзя, и дальше запустится **старая** копия скрипта.

Скрипт задаёт все вопросы сразу, потом работает молча. В конце печатает отчёт
с командой для входа и паролем и сохраняет его в `/root/node-install-report.txt`.

Неинтерактивно, с файлом ответов (образец — `config.example.conf`):

```bash
sudo bash /tmp/setup.sh /root/node.conf
```

## Главное меню

| Пункт | Что делает | Меняет систему |
|---|---|---|
| 1. Полная установка | Ставит ноду с нуля: все шаги подряд, в конце перезагрузка | Да, всё |
| 2. Компоненты | Один шаг на выбор — см. ниже | Да, выбранный |
| 3. Диагностика | Проверяет около сорока вещей и печатает список проблем | Нет |
| 4. Починка | Показывает план, спрашивает, потом чинит типовые поломки | Да, после подтверждения |
| 5. Диагностика + продление | То же, что 3, плюс `certbot renew --dry-run` | Нет |

То же без меню, когда нод много:

```bash
sudo bash /tmp/setup.sh --check     # диагностика
sudo bash /tmp/setup.sh --repair    # починка без вопросов
```

Обычный обход ноды: **3** → посмотреть → **4** → **3**.

### Чем починка отличается от установки

Полная установка ставит всё заново: сбрасывает правила ufw, пересоздаёт
контейнер, доставляет пакеты и уходит в перезагрузку. Поверх работающей ноды её
гонять не нужно.

Починка идёт по короткому списку типовых поломок. Из меню она сначала печатает
план — что именно будет сделано и что пропущено, — и ждёт ответа:
`y` выполнить всё, `s` пройтись по шагам и выбрать, `N` отмена. Флаг `--repair`
план тоже печатает, но не спрашивает: он для обхода парка нод.

Список закрытый:

| Шаг | Условие |
|---|---|
| Права 600 на файлы с секретами | Всегда |
| Харденинг SSH | Только если `sshd -T` показывает, что root или пароли открыты |
| Группа `docker` у админ-учётки | Если её нет |
| Скрипты уведомлений и systemd-юниты | Если на ноде настроен Telegram |
| Сторож панели | Если нода дежурная |
| Проверка служебных скриптов | Всегда |

Починка **не трогает** фаервол, контейнер, пакеты и nginx и **не перезагружает**
сервер. По nginx она печатает рекомендацию — что и как поправить.

Пункт 2 добавляет админ-учётку в группу `docker`, даже если Docker уже был
установлен до скрипта, — иначе `docker ps` отвечает `permission denied`.
Членство подхватывается только в новой сессии SSH. Прав это не добавляет:
у учётки и так `sudo` без пароля.

Пункт 8 — единственный, который выдаёт первичный харденинг SSH: он спрашивает
публичный ключ, проверяет его через `ssh-keygen` и только потом отключает вход
по паролю. Пункт 4 перед записью конфига nginx показывает его целиком и ждёт
подтверждения.

## nginx

Скрипт считает nginx чужой территорией: на сервере рядом с нодой может жить
другой сайт.

| Ситуация | Поведение |
|---|---|
| Починка (пункт 4, `--repair`) | Ничего не трогает. Печатает состояние, готовый конфиг, отличия от текущего и три команды |
| Ручная правка (пункт 2 → 4, смена домена) | Показывает то же самое и ждёт `y` |
| Установка на пустой nginx | Пишет сама: конфига нет, сайтов нет |
| Установка там, где уже есть чужие конфиги | Не пишет, выдаёт рекомендацию |

Правила, которые действуют всегда:

* домен ноды берётся из включённого конфига nginx, у которого есть свой
  сертификат. Сертификатов несколько и доказательств нет — скрипт ничего не
  выбирает и называет кандидатов;
* заглушка `default_server` на `127.0.0.1:8443` в nginx может быть только одна.
  Если её держит соседний конфиг, скрипт свою не добавляет;
* свои файлы помечаются строкой-меткой в первой строке. Файл без метки перед
  перезаписью копируется в `*.bak.<дата>`;
* если `nginx -t` не прошёл, конфиг возвращается из копии, а без копии —
  снимается с публикации, чтобы nginx остался рабочим.

Домен из `install.conf` имеет приоритет над определением. Если туда попал не тот
домен, исправьте руками:

```bash
sudo grep -E '^(DOMAIN|SUBDOMAIN)=' /etc/rabotahrista/install.conf
```

## Сертификат

Выпуск и продление — через webroot `/var/lib/letsencrypt`. Сертификат
выпускается, только если `/.well-known/acme-challenge/` уже отдаётся наружу:
скрипт кладёт туда случайный токен и запрашивает его через интернет. Не дошло —
печатает нужный кусок конфига и останавливается, ничего не меняя. Исключение —
пустой сервер: там сначала публикуется HTTP-часть конфига ноды, иначе отдавать
токен некому.

Проверка именно такая, а не сравнение IP, потому что за оранжевым облаком
Cloudflare IP никогда не совпадёт, а выпуску это не мешает. В TLS-блоке конфига
тоже есть путь для ACME — при «Always Use HTTPS» проверка продления приходит по
HTTPS, и без него продление тихо провалится примерно через 60 дней.

Ранние версии выпускали сертификат плагином `--nginx`, и такие ноды до сих пор
продлеваются им: плагин на время проверки сам правит конфиг. Диагностика читает
`authenticator` из `/etc/letsencrypt/renewal/<домен>.conf`. Быстрый прогон
(пункт 3) в этом случае предупреждает, что способ не наш и не проверен; пункт 5
гоняет настоящий `certbot renew --dry-run` — и если тот прошёл, претензия
снимается: работающее продление менять не нужно.

## Уведомления и мониторинг

Настраиваются пунктом 11. Уходят в Telegram с шапкой «имя ноды и её IP», чтобы
при нескольких нодах было понятно, о какой речь:

* нода упала или поднялась (`rh-node-watch`, `rh-node-health`);
* сервер загрузился;
* кто-то вошёл по SSH.

**Сторож панели** (пункт 21) включается на **одной** дежурной ноде, иначе при
падении панели напишут все разом. Связь односторонняя: панель сама подключается
к ноде и держит TCP-соединения. Нода следит за их исчезновением и дополнительно
стучится в порт панели — это ловит случай, когда панель мертва, а сокеты висят
в ESTABLISHED. Тревога после трёх провалов подряд, примерно через 6 минут:
перезапуск панели это переживает, настоящее падение — нет.

## Разработка

`setup.sh` и `check.sh` в корне **не редактируются руками** — это собранные
файлы. На чистый сервер должен приезжать один самодостаточный скрипт, поэтому
исходники живут в `lib/`, а сборщик склеивает их.

```
lib/00-header.sh      режимы оболочки, обработчик ошибок, все настройки
lib/10-helpers.sh     сводка шагов и печать итогового отчёта
lib/20-prompts.sh     все вопросы пользователю и проверка введённого
lib/30-state.sh       сохранение ответов между запусками, отправка в Telegram
lib/40-system.sh      swap, пакеты, sysctl, IPv6, ротация логов, автообновления
lib/50-security.sh    пользователь, харденинг SSH, UFW, fail2ban
lib/60-node.sh        Docker и контейнер remnanode
lib/70-web.sh         сертификат, Cloudflare DNS, конфиг nginx
lib/75-domain.sh      смена домена ноды
lib/80-notify.sh      телеграм-уведомления и сервисы слежения
lib/82-panel.sh       сторож панели на дежурной ноде
lib/85-extras.sh      WARP, speedtest, внешняя диагностика
lib/90-install.sh     порядок шагов при полной установке
lib/92-repair.sh      починка
lib/94-check.sh       диагностика
lib/95-menu.sh        меню
lib/99-main.sh        точка входа (всегда последним)

build.py              собирает setup.sh и check.sh
.githooks/pre-commit  сборка и тесты перед каждым коммитом
tests/                проверки, которые не требуют сервера
```

Файлы склеиваются по алфавиту имён — отсюда нумерация. `setup.sh` собирается из
всех модулей, `check.sh` — из `94-check.sh` плюс блок настроек из `00-header.sh`,
то есть в меню и в отдельном файле работает один и тот же код.

### Рабочий цикл

Один раз на репозиторий:

```powershell
git config core.hooksPath .githooks
```

Дальше:

```powershell
# правите нужный модуль в lib/
git add -A
git commit -m "..."     # хук соберёт setup.sh и check.sh и прогонит тесты
git push
```

Хук добавляет пересобранные файлы в тот же коммит. Красные тесты коммит
отменяют. Обойти в крайнем случае: `git commit --no-verify`.

CI на GitHub делает то же самое, но **ничего не коммитит**, поэтому `git pull`
после пуша не нужен.

Собрать и проверить вручную:

```powershell
python build.py
bash tests/run-tests.sh
```

### Тесты

`bash tests/run-tests.sh` — 23 группы, 82 проверки, сервер не нужен.

Кроме синтаксиса и `shellcheck`, проверяется:

1. Собранные файлы совпадают с `lib/`, переводы строк LF, shebang'и генерируемых
   скриптов на месте.
2. Ни одна функция не заканчивается голым условием.
3. Шаги установки не задают вопросов — все вопросы заданы заранее.
4. Опросные функции возвращают 0, когда спрашивать нечего.
5. Мусор в `ADMIN_USER` и `SSH_PORT` откатывается на значения по умолчанию.
6. Порты ноды и WARP нигде не зашиты мимо переменных.
7. Падение внутри функции печатает команду и имя функции; падение компонента не
   убивает меню.
8. Сохранённые ответы не выполняются как команды при следующем запуске.
9. Порт сверяется точно, а не по подстроке (22220 не равно 2222).
10. Битый SSH-ключ отбраковывается до того, как отключат вход по паролю.
11. Диагностика ничего не меняет и не разоружает обработчик ошибок установщика.
12. Починка трогает SSH ровно тогда, когда харденинг слетел.
13. Домен ноды не выбирается «первым по алфавиту».
14. Починка не правит nginx; ручная правка ничего не пишет без подтверждения.
15. Сертификат не выпускается, пока ACME-путь снаружи не отдаётся.
16. Админ-учётка попадает в группу `docker`, даже если Docker стоял раньше.
17. Починка печатает план и без ответа `y` не делает ничего; `--repair` не
    спрашивает.
18. Сторож панели: пять сценариев от «всё хорошо» до «сервер жив, нода не
    подключена».

Каждая проверка ловит ошибку, которая уже случалась на живой ноде.

## Если что-то пошло не так

Скрипт печатает подробность аварии: команду, функцию, строку и код возврата.
Каждый шаг изолирован — падение одного не роняет остальные, а помечается как
`[СБОЙ]` в итоговой сводке. Полный лог — `/var/log/node-setup.log`.

**Харденинг SSH** защищён отдельно. После перезапуска sshd скрипт сверяет
фактические значения (`sshd -T`) и различает три исхода: всё применилось;
конфиг принят, но порт заработает после перезагрузки (UFW при этом держит
открытым и старый порт); конфиг не читается вообще — тогда харденинг
откатывается, пока текущая сессия жива.

Полезно знать: sshd берёт **первое встреченное** значение директивы, а дроп-ины
в `/etc/ssh/sshd_config.d/` читаются по алфавиту. Файл хостера с именем вида
`00-*.conf` перебивает наш `01-hardening.conf` — после ремонта сервера вход под
root может снова оказаться открыт. Диагностика такие файлы называет по именам,
починка их комментирует с бэкапом и перезапускает sshd.
