# rabotahrista

Установщик ноды Remnawave на чистый VPS: пользователь, харденинг SSH, фаервол,
fail2ban, тюнинг ядра, Docker, сама нода, сертификат Let's Encrypt и nginx,
плюс уведомления в Telegram.

## Установка на сервер

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/setup.sh)
```

Запускать под root, на чистой Ubuntu или Debian. Скрипт задаёт вопросы,
показывает меню и в конце печатает отчёт с командой для входа и паролем.

Неинтерактивная установка — с файлом ответов:

```bash
bash <(curl -fsSL .../setup.sh) /root/node.conf
```

За образец берите `config.example.conf`.

## Как устроен репозиторий

Главное, что нужно понять: **`setup.sh` в корне не редактируется руками.**
Это собранный файл — он существует потому, что на чистом сервере нет ни git,
ни репозитория, и туда должен приезжать один самодостаточный скрипт.
Исходники живут в `lib/`.

```
lib/00-header.sh      режимы оболочки, обработчик ошибок, все настройки
lib/10-helpers.sh     сводка шагов и печать итогового отчёта
lib/20-prompts.sh     все вопросы пользователю и проверка введённого
lib/30-state.sh       сохранение ответов между запусками, отправка в Telegram
lib/40-system.sh      swap, пакеты, sysctl, IPv6, ротация логов, автообновления
lib/50-security.sh    пользователь, харденинг SSH, UFW, fail2ban
lib/60-node.sh        Docker и контейнер remnanode
lib/70-web.sh         ACME-проверка, сертификат, Cloudflare DNS, nginx
lib/80-notify.sh      телеграм-уведомления и сервисы слежения
lib/82-panel.sh       сторож панели на дежурной ноде
lib/85-extras.sh      WARP, speedtest, диагностика
lib/90-install.sh     порядок шагов при полной установке
lib/95-menu.sh        меню
lib/99-main.sh        точка входа (всегда последним)

build.py              склеивает lib/*.sh в setup.sh
check.sh              диагностика ноды, ничего не меняет (отдельный файл)
tests/                проверки, которые не требуют сервера
```

Файлы склеиваются по алфавиту имён — поэтому они пронумерованы.
`00-header.sh` обязан быть первым, `99-main.sh` — последним, это проверяется
при сборке.

## Рабочий цикл

```bash
# 1. правите нужный модуль в lib/
# 2. пересобираете
python3 build.py
# 3. прогоняете проверки
bash tests/run-tests.sh
# 4. коммитите И lib/, И setup.sh
```

Если забыли собрать — GitHub Actions пересоберёт `setup.sh` сам и закоммитит.
Но лучше собирать локально: так вы видите, что именно уедет на сервер.

## Что проверяют тесты

Сервер для этого не нужен, всё гоняется локально за пару секунд:
`bash tests/run-tests.sh` — 15 групп, 38 проверок.

1. Синтаксис каждого модуля и собранного файла (`bash -n`).
2. Сборка: `setup.sh` совпадает с `lib/`, shebang на месте, переводы строк LF.
3. **Ни одна функция не заканчивается голым условием** — см. ниже.
4. Опросные функции возвращают 0, когда все ответы уже заполнены.
5. Мусор в `ADMIN_USER` / `SSH_PORT` откатывается на значения по умолчанию.
6. Порты ноды и WARP нигде не зашиты мимо переменных.
7. Повторная установка с настроенным Telegram доходит до конца.
8. Падение внутри функции печатает команду и имя функции, а не проходит молча.
9. Падение компонента не убивает меню.
10. Сохранённые ответы не выполняются как команды при следующем запуске.
11. Порт сверяется точно, а не по подстроке (22220 ≠ 2222).
12. Битый SSH-ключ отбраковывается до того, как отключат вход по паролю.
13. `shellcheck`, если установлен.

### Про пункты 3, 7, 8 — почему это отдельные тесты

Функция в bash возвращает код последней выполненной команды. Если последняя
строка — проверка вроде `[[ -z "$TG_TOPIC_ID" ]] && read ...`, то при
несовпадении условия функция вернёт 1. А вызов

```bash
[[ -n "$TG_BOT_TOKEN" ]] && ask_telegram
```

под `set -e` в этом случае завершает **весь скрипт**. Выглядело это так:
повторная установка на сервере, где Telegram уже настроен, обрывалась молча
сразу после строки `--- Telegram-уведомления ---`.

Молча — потому что ERR-трап без флага `set -E` не наследуется функциями.
Отсюда `set -eE` в `00-header.sh`: теперь любая авария печатает команду,
функцию, строку и код возврата.

Обратная сторона: ERR-трап срабатывает **даже при `set +e`**. Поэтому меню
запускает компоненты через `menu_step`, то есть внутри `if` — только там
подавлены и `set -e`, и трап. Пункт 9 следит, чтобы это не отменили.

## Диагностика живой ноды

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/3APA3A-3AHO3A/rabotahrista/main/check.sh)
bash <(... check.sh) --deep    # + реальный тест продления сертификата
```

`check.sh` только читает — это проверяется тестом, а не обещанием. Запускать
на живой ноде безопасно в любой момент. Полную установку поверх работающей
ноды гонять НЕ нужно: она сбрасывает правила ufw, пересоздаёт контейнер и
уходит в перезагрузку. Чините точечно через меню по итогам диагностики.

## Мониторинг панели

Связь односторонняя: панель сама подключается к ноде и держит постоянные
TCP-соединения. Нода к панели не ходит, поэтому о падении панели она узнаёт
по исчезновению этих соединений — плюс сама стучится в порт панели, чтобы
поймать жёсткое падение, при котором сокеты зависают в ESTABLISHED.

Включается на **одной** дежурной ноде (пункт 21 меню), иначе при падении
панели напишут все ноды разом. Тревога — после трёх провалов подряд, то есть
примерно через 6 минут: перезапуск панели это переживает, настоящее падение —
нет.

## Файлы на сервере после установки

| Путь | Что внутри |
|---|---|
| `/root/node-install-report.txt` | итоговый отчёт: доступы, пароль, версии пакетов |
| `/var/log/node-setup.log` | полный лог установки |
| `/etc/rabotahrista/install.conf` | сохранённые ответы для будущих запусков |
| `/etc/rabotahrista/notify.env` | токены Telegram и имя ноды |
| `/etc/rabotahrista/panel.env` | настройки сторожа панели (только на дежурной) |
| `/opt/remnanode/docker-compose.yml` | конфигурация контейнера ноды |

Все пять — с правами 600, внутри секреты (в compose лежит SECRET_KEY ноды).

## Если что-то пошло не так

Скрипт печатает подробность аварии: строку, саму команду, код возврата и
функцию. Каждый шаг установки при этом изолирован — падение одного не роняет
остальные, а помечается как `[СБОЙ]` в итоговой сводке.

Харденинг SSH защищён отдельно: если после перезапуска sshd не начинает слушать
новый порт, скрипт различает две ситуации — «конфиг принят, применится после
перезагрузки» (ничего не трогаем, UFW держит открытым и старый порт) и «конфиг
вообще не читается» (откатываемся, пока текущая сессия жива).
